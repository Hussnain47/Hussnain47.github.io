Making community automation run on schedule.

Recurring campaigns across a multi-service platform, with audience batching, retries, and execution tracking.

ContextDistributed systems · Khoros Community
My roleCross-service backend implementation
TechnologyGo / Java / GraphQL / Redis
Schedule→Audience→Execute

Conceptual overview · not a production topology

The problem

Community automation needed to run on a schedule, rather than only react to a user event. Recurring email campaigns also needed to reach large audiences without turning each scheduled run into an uncontrolled database or server load spike.

My contribution

I built the scheduler and worked across the community backend and Flow services to connect scheduling, audience selection, and action execution. The implementation used Redis-cached audience data, batching, exponential retries, and fail-safes. The campaign scope included audiences of more than 100,000 users, making control over database and server load a central requirement.

Decisions that mattered

The scheduler, persistence layer, community client, and execution supervisor had separate responsibilities. Keeping those boundaries explicit made it possible to reason about a due schedule independently from an action that was already running.

Handling failure

Run completion and reliable status delivery are different properties. During QA, a run could reach completion through a supervisor retrigger even when status updates were not arriving. Investigating the timing and completion path exposed that gap; a terminal “completed” state alone was insufficient evidence that the whole feedback loop worked.

Validation and outcome

The implementation added recurring custom-email scheduling with bounded audience processing and execution tracking. Integration testing and deployment preparation were part of the delivery. QA exposed a status-update delivery gap that needed to be tracked separately from successful action execution.

What I learned

Test the behavior between services, including recovery paths. A green local test or a completed run is useful evidence only when it exercises the contract the system depends on.
